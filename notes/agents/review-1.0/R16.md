## Findings

### R16-1. The present-tense CI gate has regex gaps that let banned narrated-history wording through
- severity: major
- category: other
- location: scripts/check_temporal_wording.py:13-19 (invoked by .github/workflows/lean_action_ci.yml:40-41)
- protected: no
- verdict: confirmed
- evidence: `.claude/CLAUDE.md:16` bans, among other things, "previously", "formerly", "now …", and
  "no longer …" outright (with only in-text positional references like "as we previously proved"
  exempted). The script's `PATTERN` regex is:
  ```
  r"[Rr]ecently completed|[Ff]ormerly|earlier version|earlier draft|[Ww]as withdrawn"
  r"|was once|has since been|is now a theorem|now (carries|supplies|consumes)"
  r"|\(new\)|\bnew (layer|block|subsection|node)\b|[Nn]ewest|\bblog\b"
  r"|left for later|for the time being|v4\.\d+\.\d+-rc\d|Mathlib \(at"
  r"|\bthe former Axiom|has been (removed|replaced|split|renamed)"
  ```
  It has no case at all for the literal phrase `"no longer"`, and no general case for `"now"` (only
  three specific collocations `now carries|supplies|consumes` are caught) or for `"previously"`
  (only the docstring's own comment mentions the allowed exception; the pattern never tests for the
  word). I confirmed this by running the compiled regex against three sentences built directly from
  CLAUDE.md's banned phrasing:
  ```
  'no longer required'                                                        -> False (not flagged)
  'This is now proven in full generality'                                     -> False (not flagged)
  'We previously assumed boundedness, but this constraint no longer applies.' -> False (not flagged)
  ```
  All three are exactly the kind of history-narrating sentence the project's own policy forbids, and
  the CI gate (the sole enforcement mechanism named in CLAUDE.md and exercised by
  `lean_action_ci.yml`) would pass them silently.
- proposed fix: extend `PATTERN` with unqualified `\bno longer\b`, a broader `\bnow\b` check (narrowed
  by an allowlist of safe collocations like "now that" rather than the reverse), and a check for
  `\bpreviously\b` that excludes the "as we previously proved"-style allowlist phrase explicitly
  mentioned in the script's own docstring but never implemented.

### R16-2. `blueprint.yml` grants `issues: write` and `pull-requests: write` that no step uses
- severity: minor
- category: other
- location: .github/workflows/blueprint.yml:15-20
- protected: no
- verdict: confirmed
- evidence: the workflow triggers only on `push` to `main` and `workflow_dispatch` (lines 3-7), and
  its two steps are `leanprover/lean-action` (build+lint) and `leanprover-community/docgen-action`
  (compile blueprint+docs). Neither step files or comments on issues or pull requests. The
  `issues: write` and `pull-requests: write` permissions (lines 19-20) are unused grants, contrary to
  least privilege.
- proposed fix: drop the two unused permission lines unless a specific step (undocumented in this
  file) needs them; if `docgen-action` needs them internally, say so in a comment.

### R16-3. Inconsistent action-pinning practice across the two build workflows
- severity: nit
- category: other
- location: .github/workflows/blueprint.yml:39,44,51 vs .github/workflows/lean_action_ci.yml:21-22
- protected: no
- verdict: confirmed
- evidence: `blueprint.yml` pins `leanprover/lean-action` and `leanprover-community/docgen-action` to
  full commit SHAs with a trailing date comment (`@434f25c2f80ded67bba02502ad3a86f25db50709 # 2025-07-02`,
  `@7b5b9a1822650bd45aaeb4182d94bceba2030f89 # 2026-04-14`) and uses `actions/checkout@v6`, while
  `lean_action_ci.yml` uses the floating tags `actions/checkout@v5` and `leanprover/lean-action@v1`.
  Within `blueprint.yml` itself, `jlumbroso/free-disk-space@main` (line 28) is pinned to a floating
  branch ref, next to two SHA-pinned actions in the same file. The two workflows building the same
  project disagree on both the checkout major version and the pinning discipline for `lean-action`.
- proposed fix: pick one pinning policy (SHA+date comment, consistently) and one `actions/checkout`
  major version, and apply both across all workflow files.

## Summary

Counts by severity: major 1, minor 1, nit 2 (one of which, R16-4, is a clean-bill record rather than
a defect).
Counts by category: other 3, home-page 1.

Top findings, in order of how much they'd matter for a 1.0 release:
1. **R16-1** (major) — the present-tense CI gate (`scripts/check_temporal_wording.py`, run by
   `lean_action_ci.yml`) does not actually implement CLAUDE.md's stated ban on "no longer", general
   "now", and "previously"; confirmed by running the regex against test sentences built from the
   policy text itself.
2. **R16-2** (minor) — `blueprint.yml` grants `issues: write` / `pull-requests: write` that no step
   in the workflow uses.
3. **R16-3** (nit) — `blueprint.yml` and `lean_action_ci.yml` disagree on `actions/checkout` major
   version and on whether third-party actions are pinned by SHA or floating tag; `free-disk-space@main`
   is unpinned next to two SHA-pinned actions in the same file.
4. **R16-4** — nav reachability, cross-page link consistency, and `guide.md`'s page/declaration-count
   claims all verified correct; no finding.

Cross-cutting pattern: the two build-and-check workflows (`blueprint.yml`, `lean_action_ci.yml`) were
evidently edited independently over time (different checkout versions, different `lean-action` pinning
style, different permission scopes) — worth a single pass to reconcile pinning/permission policy across
both files rather than fixing each inconsistency in isolation.

What I verified with a tool vs. by reading: R16-1 verified by executing the compiled regex against
constructed test strings (`python3`); the 341-page and 662-declaration claims in R16-4 verified via
`pdfinfo` and `grep -c` counts. R16-2 and R16-3 are verified by reading the workflow YAML directly (no
tool needed beyond grep/read). The three skipped items are explicitly marked as not independently
verified, with the reasoning for not flagging them.
