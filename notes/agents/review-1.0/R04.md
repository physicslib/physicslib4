## Findings

### R04-1. `prpstn:hall-10.3`'s `\uses{}` tag claims a dependency the Lean proof does not take
- severity: minor
- category: uses-tags
- location: `blueprint/src/sections/sec10/unbounded-spectral-theorems.tex:1773` (the `\uses{}` of
  `prpstn:hall-10.3`) paired with
  `Physicslib4/Spectral/Unbounded/Integral.lean:1131` (`isSelfAdjoint_pmapIntegral_of_real`)
- protected: no
- verdict: confirmed
- evidence: the blueprint's `\uses{}` list for `prpstn:hall-10.3` includes
  `prpstn:hall-9.26-internal, ..., def:internal-orthogonal-decomposition,
  lmm:internal-decomposition-unitary, ..., prpstn:hall-9.26`, matching the blueprint's prose proof
  (lines 1774–1816), which decomposes `H` into an internal orthogonal sum of spectral subspaces
  `H_n` and invokes `prpstn:hall-9.26-internal` to get essential self-adjointness and then
  self-adjointness. The Lean proof of the same node,
  `isSelfAdjoint_pmapIntegral_of_real` (`Integral.lean:1131`), instead derives self-adjointness
  directly: it shows `∫ f dμ - c 1` is onto `H` for non-real `c` by exhibiting an explicit bounded
  right inverse `∫ (f - c)⁻¹ dμ` (`pmapIntegral_sub_smul_integral_inv`,
  `range_subSmul_pmapIntegral_eq_top`), then concludes via `adjoint_eq_of_range_eq_top`. Tracing
  the call chain (`isSymmetric_pmapIntegral_of_real`, `dense_integralDomain`,
  `isSymmetric_iff_le_adjoint`, `orthogonal_range_subSmul`, `Submodule.top_orthogonal_eq_bot`,
  `LinearPMap.isSelfAdjoint_def`, `adjoint_eq_of_range_eq_top`) shows none of it touches
  `DirectSum.lean`; a `grep` for `IsInternalDirectSumOperator`,
  `isEssentiallySelfAdjoint_of_isInternalDirectSumOperator` etc. outside `DirectSum.lean` returns
  no hits. So the Lean formalization proves the same *statement* by a genuinely different
  argument, and the blueprint's `\uses{}` edge for this node is stale relative to the Lean proof
  (it documents the blueprint's own argument, not the formalized one). This does not affect
  correctness of the statement, only the dependency graph's accuracy for this node.
- proposed fix: either add a note to `prpstn:hall-10.3` acknowledging the Lean proof uses a
  different (resolvent-construction) argument than the one given in the prose, or trim the
  `\uses{}` edges to `prpstn:hall-9.26`/`prpstn:hall-9.26-internal` and the internal-decomposition
  definitions, since Theorem 10.4 (out of scope, not yet audited) is stated as the place that
  still needs `prpstn:hall-9.26`'s construction directly (per lines 853, 1763), so that
  proposition itself is not orphaned — only this one `\uses{}` edge is inaccurate.

### R04-2. Unexplained `erw` in `DirectSum.lean`
- severity: nit
- category: lean-style
- location: `Physicslib4/Spectral/Unbounded/DirectSum.lean:262,294,467`
- protected: no
- verdict: confirmed
- evidence: `erw [apply_single_of_isDirectSumOperator hT i ξ]` (line 262),
  `erw [apply_single_of_isDirectSumOperator hT i (η i)] at this` (line 294), and
  `erw [apply_of_mem_summand hT m ξ]` (line 467) — none carries a comment explaining why `rw`
  does not suffice (typically a reducibility/defeq mismatch through the `LinearPMap` coercion).
  This is exactly the "unexplained `erw`" pattern the review brief asks to flag; these are also
  the kind of thing that tends to break silently on a Mathlib bump.
- proposed fix: add a one-line comment at each site naming the defeq that forces `erw` over `rw`,
  or replace with an explicit `show`/`simp only` + `rw` if feasible.

### R04-3. `pmapIntegral`/`integralApply` are total via a `Classical.choose`/junk-value fallback for non-measurable `f`
- severity: nit
- category: definition-correctness
- location: `Physicslib4/Spectral/Unbounded/Integral.lean:666-679` (`integralApply`) and
  `:706-712` (`pmapIntegral`)
- protected: no
- verdict: confirmed
- evidence: `integralApply` is defined as
  `if h : Measurable f ∧ ∃! χ, ... then h.2.choose else 0`, so for a non-measurable `f` the
  operator `pmapIntegral μ f` is defined (with domain `integralDomain μ f`, itself defined via
  `MemLp f 2 (μ.assoc ψ)` regardless of measurability) but every value is silently `0`. This is
  the standard Mathlib-style junk-value totalization and *is* disclosed in the docstring ("The
  measurability guard makes `pmapIntegral` linear by a direct argument; every result about
  `pmapIntegral` assumes `f` measurable anyway"), so it is not a hidden trap — flagging only
  because the review brief specifically asks to look for junk-value patterns, and because the
  blueprint's `prpstn:hall-10.1` states existence/uniqueness only for measurable `f` and never
  mentions the non-measurable case, so a reader comparing blueprint to Lean signature without the
  docstring could be misled into thinking `pmapIntegral` is total in a mathematically meaningful
  sense.
- proposed fix: none needed beyond what's already in the docstring; could optionally add a
  one-line remark in the blueprint's convention (`conv:section-integration`) noting that the Lean
  operator is total with value `0` off the measurable case, for readers who inspect the Lean
  signature without the docstring.

## Summary

No mismatches of classification "Lean assumes more / concludes less / different objects / edge
cases differ" were found for any of the ~35 blueprint nodes with `\lean{}` tags in scope
(`def:hall-3.1` through `prpstn:hall-10.3`, plus the direct-sum apparatus in `DirectSum.lean`).
Every definition checked — unbounded operator, adjoint, symmetric, self-adjoint, essentially
self-adjoint, closed/closable, kernel, range, resolvent set/spectrum, quadratic/sesquilinear form
on a subspace, the integral against a PVM (`integralDomain`/`integralForm`/`pmapIntegral`) — has a
Lean signature that matches the blueprint's hypotheses, quantifiers and conclusion on direct
reading. The one place where blueprint and Lean genuinely diverge (R04-1) is at the level of
*proof strategy*, not statement, and only affects a `\uses{}` edge's accuracy.

Cross-cutting pattern worth noting for a staged fix plan: this section's blueprint prose is
unusually careful about exactly stating which Mathlib primitives are used for each
`\lean{}` tag and about density-free vs. dense-domain distinctions (e.g. `IsPositive`,
`IsSymmetric` are deliberately *not* required to have dense domain, matching the blueprint's
explicit remark in `def:positive-unbounded-operator`). The Lean code mirrors this discipline
closely. The main risk surface found is proof-strategy drift from the blueprint's prose proof
(R04-1), which is likely to recur wherever a Lean proof takes a shortcut the blueprint prose does
not anticipate — worth a pass that diffs `\uses{}` edges against actual proof-term dependencies
across the rest of chapter 10, not just this section.
