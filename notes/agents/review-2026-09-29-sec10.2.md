## Findings

### Medium

**M1. `verify-receipt.json` is stale relative to in-scope sources.**
`.git/lean-kit/verify-receipt.json` records `lake build`/`lake lint` passing at
`2026-09-18T14:08:28+00:00`. Commits `26ca993`, `effd1f5`, `15b3ce6` (2026-09-24
through 2026-09-26) touched in-scope files (`Physicslib4/Spectral/Basic.lean`,
`BorelClasses.lean`, `Spectrum.lean`, plus `SpectralTheorem.lean` etc. via
`git log --name-only`) after the receipt's timestamp, so the recorded verify
run does not cover the current tree. Mitigating evidence: `.lake/build/lib/lean`
oleans for the touched files are dated 2026-09-26 (matching the last commit),
and my own `lake env lean` run against the current sources succeeded with a
clean axiom set, so the build is not actually broken — the receipt is just
out of date. **Previously reported** (2026-09-25 and 2026-09-26 memos), still
open.

**M2. `existsUnique_realCalculus`/`realCalculus` take a materially different
proof route than the blueprint narrates, and part of `prpstn:hall-8.3`'s
`\uses{}` graph is not actually exercised by that route.**
`Physicslib4/Spectral/ContinuousCalculus.lean:236-274`. The blueprint's proof of
`prpstn:hall-8.3` (lines 3021-3132) builds the real continuous functional
calculus by hand from `thrm:stone-weierstrass-real`, `lmm:hall-8.1` (‖A‖ =
spectral radius for self-adjoint `A`), `prpstn:hall-7.5`/`7.7`, and the Neumann
series/resolvent apparatus developed earlier in the chapter. The Lean
`realCalculus` is instead defined as Mathlib's general-purpose `cfcHom hA`
(continuous functional calculus for C⋆-algebras), and `existsUnique_realCalculus`
packages `cfcHom` plus `norm_cfcHom` for existence, using Stone–Weierstrass only
for the uniqueness half. This substitution is disclosed in the Lean docstring
("Using `cfcHom` rather than extracting a map from `existsUnique_realCalculus`
keeps the definition independent of any unproved statement...") but the
blueprint's own proof text is not annotated to say that the Lean proof takes
this shortcut, so a reader following blueprint → Lean has no signal that the
elaborate resolvent/spectral-radius apparatus built earlier in the chapter is
not what actually discharges `prpstn:hall-8.3` in Lean. This is a documentation
gap, not a soundness problem — I did not find evidence that the earlier
apparatus (Neumann series, `mem_resolventSet_of_norm_lt`, `lmm:hall-8.1`, etc.)
is dead code; those results are also used to establish `prpstn:hall-7.5`,
`prpstn:hall-7.7`, and `def:spectral-radius` themselves, which are asserted (and
in Lean, `\lean`-tagged) independently of `prpstn:hall-8.3`. **New this
session** — not found in the 2026-09-25/26 memos' grep for "cfcHom" /
"different route" language.

### Low

**L1. `functionalCalculus` is total with a silent junk-value fallback, and the
fallback is documented one file away, not at its own declaration.**
`Physicslib4/Spectral/SpectralTheorem.lean:928-930` defines
`functionalCalculus hA f := (spectralMeasure hA).integral f` for *any*
`f : spectrum ℝ A → ℂ`, i.e. without a "bounded and Borel-measurable" hypothesis
that the blueprint's `def:functional-calculus` (lines 5815-5823) states as a
premise ("If ... `f` is a bounded measurable function ..."). The underlying
`ProjectionValuedMeasure.integral` (`Physicslib4/Spectral/OperatorIntegral.lean:
416-422`) is defined by `if h : f ∈ BddMeasurable X then ... else 0`, and that
`0` fallback **is** documented at `integral`'s own docstring ("defined to be `0`
on functions that are not bounded and measurable"), but `functionalCalculus`'s
docstring does not repeat or cross-reference this, so a reader who only opens
`functionalCalculus` would not learn that `f(A)` silently becomes `0` outside
the blueprint's intended domain of `f`. Benign (matches on the intended domain,
which is all that downstream theorems use), but worth a one-line docstring
addition. **Previously reported** (2026-09-26 memo, "junk values `0` for
`ProjectionValuedMeasure.integral`/`borelCalculus`/`functionalCalculus`"),
re-verified unchanged.

**L2. `spectralRadius` is Mathlib's general `ℝ≥0∞`-valued notion; the blueprint
states `R(A)` as "a finite real number."**
`def:spectral-radius` (lines 2542-2552) asserts `R(A) ∈ ℝ` (finite, using
`prpstn:hall-7.5`). The tagged Lean `spectralRadius` (`Mathlib/Analysis/Normed/
Algebra/Spectrum.lean:53-55`) is `ℝ≥0∞`-valued for a general normed algebra
(can be `0` for empty spectrum, `∞` for unbounded spectrum). This is a
"notation only" mismatch given the operator-algebra context at hand: the later
node `IsSelfAdjoint.toReal_spectralRadius_complex_eq_norm` explicitly takes
`.toReal`, so Lean already reconciles the two. Not a narrowing; flagged only
because the blueprint text asserts a typed fact ("is a finite real number")
that isn't literally the type of the tagged declaration. **Previously
reported** (2026-09-26 memo, item near line 62), re-verified unchanged.

**L3. `nolint unusedArguments` on `Physicslib4.Spectral.L0`.**
`Physicslib4/Spectral/BorelClasses.lean:279-282`. Justified by the adjacent
docstring (lines 264-278): the blueprint's `𝓛₀` definition asks that `E` be
measurable, but this is not carried as a conjunct because it is derivable
(pointwise limits of continuous functions valued in `[BorelSpace X]` are
automatically measurable), so the `X`/instance arguments look unused to the
linter even though they parametrize the ambient space. Comment present and
substantive — not a lint-gate workaround. **Previously reported**, re-verified
unchanged.

**L4. `tendsto_integral_of_boundedPointwiseLimit` adds an explicit
measurability hypothesis the blueprint leaves implicit.**
`Physicslib4/Spectral/Basic.lean:786-797` requires `∀ i, Measurable (f i)`,
which `thrm:bounded-convergence-theorem` (lines 3866-3874) does not state as a
hypothesis (it only says "uniformly bounded ... functions that converge
pointwise"). The Lean docstring explains this directly: "the blueprint leaves
it implicit in writing `∫_X f_i dμ`, but the integral is only defined with it."
Disclosed, and required for the statement to typecheck as an integral
identity — not a narrowing in substance. Not previously flagged by name in the
2026-09-26 memo's summary list, but consistent with its "documented,
benign generalization" characterization of the file as a whole; not counted as
new since it is the same category of finding already characterized there.
